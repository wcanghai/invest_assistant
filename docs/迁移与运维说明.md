# 重构迁移与运维说明

## 迁移前检查

1. 导出并暂停两个 `Invest-*` Windows 定时任务，确认无项目写入进程。
2. 使用项目 Python 执行 `python -m invest db check`。
3. 运行 `python -m invest db migrate`。命令先拒绝已有目标，然后通过 SQLite
   备份 API 制作包含已提交 WAL 数据的一致性副本。随后只从备份复制到隔离暂存库。
4. 发布前自动核对 37 张业务表的全部行摘要、结构、索引、触发器、自增序列，
   并执行 SQLite `quick_check` 和 `foreign_key_check`。这不等同于执行
   `integrity_check`。四库发布成功后写入 `data/databases/migration_manifest.json`。
5. `python -m invest db verify` 可重新比较目标库与固定备份。
   正式运行产生新行情或新日报后，差异属于预期；不能将迁移基线校验当作日常健康检查。
   日常用 `python -m invest doctor` 检查库是否可读，并检查业务任务的真实输出。

复制失败时正式路径不发布新库，备份及暂存目录保留用于排错。
发布中断可能留下部分目标文件，但不会生成成功清单；先核对并归档这些文件，再重试。
新账户库只初始化为空；若源库出现清单以外的账户表，迁移拒绝继续，必须单独制定映射。

## 定时任务切换与回滚

运行 `scripts/deploy_tasks.ps1 -WhatIf` 先检查迁移清单、实际配置、数据库和任务归属。
正式执行时备份任务 XML 并启用已有任务，保留触发器和权限；不会重新注册或立即执行。
没有成功迁移清单、目标为空、配置不一致或任务仍在运行时会拒绝部署。
两个任务继续每十分钟检查；需要验证时通过任务计划程序显式触发，并检查日志和数据库。

回滚时使用 `scripts/rollback_tasks.ps1 -TaskBackupDirectory <备份目录>` 恢复 XML。
这只恢复任务定义，不恢复源码或数据库。恢复前必须停止项目写入进程，并通过 SQLite
备份 API 保留切换后的数据库，尤其是账户和成交数据；不能用文件覆盖丢弃新增数据。
代码和配置须另行恢复到匹配旧库的版本，验证后再启用任务。

日报任务退出码 0 表示该次调度程序正常退出，不意味着全部行情已补齐。
`data/state/report_schedule.json` 保存批次和补跑状态；`backfill` 中的 false 表示待重试。
当前沿用原行为：晚间采集合并完成当日到期批次，报告保留真实采集时间，不能视作恢复早盘快照。
